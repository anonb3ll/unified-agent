- **`obsidian_append` no longer writes over a lock another hub writer adds
  mid-append (#1890).** The lock check, the plugin PATCH and the re-check now
  run under the per-note advisory lock that `vault_write` and `vault_journal`
  also take, and the PATCH carries the plugin's `ifMatch` version of the note
  the hub checked. A note changed before the plugin read it is refused with
  "note changed or locked since check" and nothing is written. An edit made in
  the Obsidian UI or by sync after the plugin's own read is still not fenced;
  `locked_after_write` reports a lock that survives the write, as before.
  A PATCH that times out after it was sent fails with "outcome unknown" and
  holds the note lock up to 5 seconds for the plugin's late write; a later write
  is still not fenced. The lock check and version read a large note in bounded
  chunks instead of whole.
  The per-note lock is now a sidecar file under `$UA_HOME/locks/vault` keyed by
  the note's path, so a writer that replaces the note atomically no longer
  escapes it and a new note is fenced too; `vault_journal` takes the same lock.
  The `ifMatch` version drops a leading UTF-8 BOM as Obsidian's `vault.read`
  does, so appends to a BOM note are no longer refused with 412. A note the hub
  cannot read is refused with a "cannot read note" error instead of a raw
  `PermissionError` or a write past an unverified lock.
