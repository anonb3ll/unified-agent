- An approval pass is now bound to the person it was granted for (#2492). The gate matched an approved row on tool, payload and tenant only, so a second eligible caller making the identical call consumed the first caller's one-shot pass. A pass is spendable by exactly two parties: the requester that queued it, and the human who resolved it — the human-in-the-loop shape where an agent asks, a person accepts, and that person's session runs the call (elicitation, the GitHub App check, Control Center writes). A server-side on-behalf-of spend, such as applying an org proposal whose pass names the proposer, is an explicit argument rather than an implicit match, and the consumption compare-and-swap pins the row's requester too. A pending row is a request, not authority, so it is still reused across callers; a denial stays action-scoped; a pass that named no requester stays unbound (the in-process path where the tool supplied no label); and tenant fencing, operator self-approval and the pass TTL are unchanged.
