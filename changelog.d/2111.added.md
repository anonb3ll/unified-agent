- **Revision-aware vault writes (#2111).** `vault_read` now returns `revision`,
  `sha256:<hex>` of the note's raw bytes on disk, and every successful
  `vault_write` returns the note's new revision. `vault_write` takes an optional
  `expected_revision`: the write (overwrite, append or template) lands only if
  the note is still at that revision, checked inside the per-note lock after the
  `locked: true` guard, so two agents that read the same revision cannot both
  write and the second gets an error naming the current revision. `"absent"`
  means create-only. Omitting it keeps today's unconditional write. A new hub
  setting, `UA_VAULT_REQUIRE_REVISION=1` (default off), refuses an overwrite of
  an existing note without a revision; creates and appends stay allowed.
- The hub's own read-modify-write vault writers now pass the revision they
  read: `memory_promote` (learning page and `Wiki/Index.md` block) and the
  planning loop (plan page, decision packet, goal proposals) write through the
  new `vault_write_merged`, which re-reads, rebuilds and retries up to three
  times on a conflict and then fails rather than writing blind. The delegation
  ledger creates its month page create-only and appends if another writer got
  there first, instead of overwriting it. All of them work with
  `UA_VAULT_REQUIRE_REVISION=1`.
- Whole-page regenerations surface concurrent-edit conflicts instead of retrying
  stale content against a newer revision. Internal snapshots normalize LF/CRLF/CR
  text while hashing the original bytes, retaining legacy plan compatibility.
