- **A fresh `scripts/cloud-ci.sh` run no longer overwrites a newer run on the
  same head (#2211).** The check that refuses to post when the newest status of
  a context names another build ran only for `--reconcile`, so with a zombie
  watcher and a fresh run on one SHA the older build could write last (a stale
  success over a newer failure). The check now names this run's own build and
  runs before every final write, fresh or re-attached, including the exit-time
  recovery, even when none of the run's own writes landed: a fresh run notes
  the newest status id before submitting, and any other build's status past
  it, anywhere in a context's history, is a newer run, including one posted
  before this run's own pending writes, which are checked the same way; if
  the statuses cannot be read there, nothing is posted and the run prints
  the `--reconcile` command for its build. A fresh run records its
  classifier's js/native result on the build as tags, and `--reconcile`
  settles `CI / js` and `CI / desktop-core` from them, rather than only when a
  status already names the build, so a watcher whose writes all failed can
  still be re-attached and a skipped leg is never posted as passed. Which run
  is newer is decided by build creation time, not by the order statuses were
  posted, so an older build's watcher that finishes late no longer stops the
  newer build from posting its result over it. A status that cannot be proved
  older (no build named, an empty description, a failed lookup) refuses
  wherever it sits in a context's history, and contexts match without case,
  as on GitHub, in the C locale whatever the caller's (under a Turkish locale
  `CI` lowercased to a dotless `cı` and the guard matched nothing).
  GitHub statuses have no compare-and-set, so a seconds-wide window between
  that check and the writes remains, and is documented. Reconciling the same
  build twice stays allowed and posts the same statuses.
