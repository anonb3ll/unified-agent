- **Approval Ledger rows whose pending status never posted are retired when their PR closes (#2103).** Before this fix, a `github_app.process_pr_event` row whose pending-status POST failed stayed in the approval queue after its pull request closed. Each poll now reads the PR from GitHub, at most 10 per poll, and expires the row when GitHub reports the PR merged, closed or open at a different head. The expiry is recorded on `connector.github.orphan_retired`. A row for the merged head that a policy authorization covers still gets its policy-authorized success status. The poll reads the least recently checked PRs first, so rows it can never retire cannot hold newer ones back. A PR still open at the row's head keeps the row, as do a live approved pass inside its TTL and a failed GitHub read. The policy decision is committed, with a fresh denial check, before the status is posted. A retry reads GitHub before posting, so it never posts the success twice. A corrupt rotation file is ignored. Every pending row of the pull request is fenced before a policy status is posted. A retry proves the status absent, reading every page, before posting. An unposted decision whose authorization was withdrawn is cancelled. The authorization is re-verified right before every policy status POST. App reconciliation will not claim absence when a head has more check suites than GitHub's listing covers. Hub credential changes and the policy POST share one fence, covering managed `agent-token:` secret writes and deletes and the token-file rollback of `unified-agent init`. A success posted while its authorization was withdrawn outside hub code is corrected and recorded, also when the POST response, the post-POST check or the withdrawal record was lost: a success not durably verified after its POST is re-verified before its evidence is completed. App reconciliation only trusts runs carrying the poll's own external id. Unfinished policy publications are retried in rounds in commit order, with pending corrections in their own slots ahead of plain retries. Neither a publication that keeps failing (or crashing the worker) nor a stream of newer publications can starve the correction of a withdrawn success. The fixed-size retry state uses no clock and advances per attempt, and the queue attempted first alternates every poll, so a retry that keeps crashing the worker cannot block the other queue. A publication whose authorization no longer verifies is retried with the corrections, and sorting retries into queues verifies the event hash chain once per poll, even when that verification fails. A pending correction keeps the Approval Ledger poll at its active cadence.
