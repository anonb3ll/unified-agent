- **Task writes that skipped the revision now stamp one (#2087).** Two writers changed a task row without advancing `updated_at`, so a caller holding the old revision passed `task_update(expected_updated_at=...)` over a change it never saw: the `[review: merged @ ...]` note the mission merge adds in a second transaction after the durable closeout, a subtree-hold restore clearing a hold's cancel request, and the run-cache writes that run in a transaction of their own after the release committed (`record_abandoned`, the standalone `record_claim`/`record_transition` and the renewal backfill), which changed `current_run_id` and `cancel_requested`. All now stamp `storage.next_task_revision`; the backfill stamps only on an actual cache change. The revision tripwire (`tests/test_task_revision_writes.py`) now also fails on any `UPDATE tasks` that writes no `updated_at`, unless it is listed, one entry per site, as sharing a transaction and control-flow path with a revision-stamping write (checked by the scan, including commits hidden in a known committing helper) or as revision-neutral bookkeeping (lease renewal, the run-ledger cache, schema migration, hub checkout bind/release), each with a reason.
