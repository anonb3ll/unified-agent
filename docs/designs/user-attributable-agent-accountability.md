## The Thesis (arrived at late, and it is the point of the session)

> **People need to prove which human is accountable for what an AI did.**
> Not what the agent did — who is answerable for it.

Agent attribution is a logging feature. User attribution is a liability
instrument, and liability is where budget lives. Every funded competitor in the
landscape attributes at the agent, tool, or service-account level, which satisfies
an audit log and does not satisfy a risk officer: you cannot hold an API key
responsible.

Source is not inference. The author sells compliance-driven software managed
services at Usablenet and hears the objection directly across accounts:
*"there needs to be user specific audit trails and user specific accountability."*
Buyers want AI; risk blocks it; what unblocks it is proof of an accountable human.

**Corroborating incident:** the February 2026 Antigravity ban wave. Google's only
enforcement instrument was suspending the *account* — the human — because that was
the one identity it could hold responsible. It had user attribution and nothing
else. Enterprises need both ends of the chain: human -> agent -> action -> evidence.

**The identity chain is already half-built, by infrastructure rather than code.**
The whole system runs over Tailscale — this session itself was conducted over mosh
across a tailnet. Tailscale issues per-user and per-device identity at the network
layer, so the chain does not start at an API key:

```
tailnet identity (the human) -> device -> per-agent bearer token -> action -> audit row
```

Cloud gateway vendors sit in a datacenter and resolve to a service account. A
tailnet-hosted hub resolves to *which person, on which of their machines,
authorized which agent to do what.* Two of the four links come free from
infrastructure already in production here. That is the technical answer to
"user-specific accountability," and it is not available to a vendor whose control
plane lives away from the developer's machines.

**Go-to-market shape (resolves the P4 dispute between the advisor and Codex — both
were half right):**

| Layer | Buyer | Motion | Price |
|---|---|---|---|
| Local hub: context, memory, gates, multi-client, multi-device | Developers | Bottom-up install; T3 Code is one channel | Free |
| Attribution + evidence layer: human -> agent -> action -> proof | The accountable owner (risk, platform, compliance) | Top-down compliance sale | Paid |

Developers adopt what is free and useful. Risk owners buy what is provable. The
author has unusual access to both sides — the developer side through the OSS
surface and a personal line to Theo Browne, the enterprise side through a full-time
job selling compliance-driven managed services. Almost nobody building in this
category has the second.

## Problem Statement

unified_agent is 54 days old, 107,150 lines of Python, ~101 MCP tools, 25 systemd
units, ~600 commits, running in production across three machines with six-plus
heterogeneous agent clients. It works. It has never been used by anyone but its
author.

Four prior /office-hours sessions on this repo all ran Builder mode. The project
was framed on 2026-07-23 as "a hobby/learning exercise, not a push to ship new
product features." This is the first session to ask whether it is a product, and
what its market is.

The finding is not that the product is weak, and it is not — as this session first
concluded — that the author avoids contact. He sells enterprise software services
for a living and is comfortable calling the maintainer of the client project
directly. The finding is that **the substrate was built before the thesis was
stated, and the thesis came from the day job rather than the codebase.**

Three advisor conclusions were overturned during the session by facts the author
held: that comprehension was the binding constraint, that no channel existed, and
that the accountable buyer was unreachable. All three were wrong in the same
direction — underweighting assets already in hand.

## Status Quo

Asked what a would-be user does today instead, the answer was **"Nothing — they
run one agent at a time."** The behavior unified_agent governs is not yet common.
There is no bad workaround to beat; the situation is avoided rather than solved.

This makes the project a **timing bet**, not a demand bet. Timing bets are
validated by finding the small number of people already living in the future, and
they die by building for years while waiting for everyone else to arrive.

## The Wedge Vertical: agent-attributed compliance remediation

Named by the author late in the session and it is the sharpest framing produced:
not "agent governance for enterprises" (a category) but a specific first market.

> **Accessibility remediation is moving to AI agents. Compliance departments have
> to prove who fixed what. Attribute every remediation to a model, a client, a
> device, and a user.**

Shape: an accessibility-QA MCP alongside the unified_agent MCP. The compliance
department gets remediation history with attribution columns instead of a vendor's
attestation. (The author's employer has an accessibility-QA MCP forthcoming; it is
unannounced, and this is a *complement*, not a competing remediation product. The
author would not build a competing remediation service.)

**Why this beats the horizontal framing:**
- **The buyer exists and already buys evidence.** Accessibility compliance is
  litigated — demand letters, WCAG conformance, VPATs. Proof-of-remediation is
  already a line item; nobody needs convincing it is a product.
- **Two forcing functions land on one desk.** ADA and the European Accessibility
  Act make the remediation provable; the EU AI Act makes the *agent that performed
  it* provable. One department, two regulations, one gap between them.
- **The attribution dimensions are already columns.** Model, client, device, user
  map to per-agent tokens, tailnet device identity, commit co-author trailers, and
  the delegation ledger. That is a report, not a build.
- **Demonstrable rather than architectural.** "Here is the remediation, the model
  that made it, the client it ran in, the machine it ran on, and the person
  accountable." No MCP literacy required to evaluate it.
- **Expands correctly.** Accessibility remediation -> any regulated remediation ->
  all agent work.

**The discovery question this creates, and it should replace the generic one in at
least two of the five calls:** does a compliance department believe
AI-performed remediation requires *different evidence* than human-performed
remediation? If yes, there is a product. If the answer is "remediation is
remediation, the vendor attests either way," the vertical thesis needs rework —
and that is worth learning in two weeks rather than month six.

## The Pitch

**Vertical-first (preferred — names a buyer with an existing budget line):**

> Accessibility remediation is being handed to AI agents. Compliance departments
> have to prove to regulators and plaintiffs who fixed what — and when an agent
> does the fixing, that proof does not exist. We attribute every remediation to the
> model that made it, the client it ran in, the device it ran on, and the human
> accountable for it. Accessibility is where the deadline is hardest; every
> regulated remediation workflow has the same gap.

**Horizontal (the general case, for the second slide):**

*Every AI agent action, traceable to the human accountable for it.*

Enterprises want AI agents writing code. Their risk functions will not sign off,
and the objection is always the same: **we cannot say who is answerable for what
the agent did.** Existing agent-governance tools log at the agent, tool, or
service-account level — which satisfies an audit log and not a risk officer,
because you cannot hold an API key responsible.

We bind every agent action to an accountable human: **person -> device -> agent ->
action -> evidence.** The local hub is free and developers adopt it because it
makes multi-agent work bearable. The evidence layer is paid, and the buyer is
whoever's name goes on the approval.

**Why now.** EU AI Act high-risk provisions became enforceable August 2026 and
audit logs are the named conformity artifact. Gartner puts 86-89% of agent pilots
dying before production on governance gaps. Google's February 2026 ban wave
suspended paying customers because account suspension was the only accountability
instrument available to it.

**Why us.** The founder sells compliance-driven managed services to enterprises
full time — this objection is the day job, not desk research. And has run a
six-agent, three-machine fleet in production for two months: 407 merged PRs across
8 repos, including 20+ merged with CI entirely dark. GitHub reports one human wrote
392 of those pull requests; six agent identities across five model families
actually did. **That gap is the product.**

**What we have learned.** Buyers describe the requirement in near-identical
language across accounts — *user-specific audit trails, user-specific
accountability.* Nobody sells it.

## Market Landscape (web search, September 2026)

- **"MCP gateway as governance control plane" is a crowded, funded category**
  using near-identical vocabulary: MintMCP ("identity, access, memory, monitoring,
  audit"), Obot ("AI agent control plane governance playbook"), Composio ("MCP
  gateway governance"), plus competitive roundups. All are cloud / server-side /
  enterprise-sold.
- **Regulatory tailwind is real and dated.** EU AI Act high-risk provisions fully
  enforceable August 2026; gateway audit logs cited as the primary
  conformity-assessment evidence artifact. Gartner: 86–89% of agent pilots fail
  before production, blamed on governance gaps and audit blind spots. MCP on
  10,000+ enterprise servers, 97M SDK downloads by April 2026.
- **Local cross-client memory is already solved by others.** AgentMemory (May
  2026) wires Claude Code, Codex, and Cursor into one local server.
- **Dispatch is standardizing.** Agent Client Protocol (ACP): Zed Aug 2025,
  JetBrains joined, ACP Registry launched Jan 2026, remote transports on roadmap.
  OpenClaw already dispatches to Claude Code / Codex CLI / Cursor over it. This
  commoditizes exactly the client-adapter surface that took 54 days to build.
- **The February 2026 Antigravity ban wave is a dated, public proof of the
  identity gap.** Google suspended accounts — including paying AI Ultra
  subscribers at $250/month — for driving Antigravity from third-party tools
  (OpenClaw, OpenCode). The Antigravity Additional Terms forbid third-party
  software accessing the service. Accounts were later restored with a promised
  reinstatement path; the terms did not change. Note *why* the enforcement was a
  blunt account ban: the vendor had no way to tell what the third-party tool
  actually did. No per-agent identity, no attestable record, no instrument finer
  than suspension. That is premise P3 with an incident attached.

  **The direction of the call is the whole distinction.** Banned: a third-party
  client consuming Antigravity's OAuth and quota. Sanctioned: the Antigravity
  client calling out to an MCP server, which is its own documented extension
  point. unified_agent has operated on the second pattern for three months without
  incident. This is why a t3code Antigravity *provider* is unshippable while an
  Antigravity-to-unified_agent MCP connection is not.
- **Agent identity has NOT converged.** No dominant standard for signed long-lived
  agent credentials; enterprises improvise with JWTs, mTLS, cloud managed
  identities. This is the one open lane, and it is where per-agent tokens and
  per-user key acceptance sit.

**Claimed insight (Layer 3):** governance products are cloud/server-side and

## Approaches Considered

### Approach A: Land the Antigravity provider upstream — DEAD (ruled out in session)
Rejected on ToS, not on code. A t3code *provider* makes T3 Code the client driving
Antigravity's OAuth and quota — the exact shape of the February 2026 ban wave
(OpenClaw, OpenCode). T3 Code ships App Store and Play Store apps; that would
expose its users' Google accounts. No PR fixes a contract, and declining it was
correct. (The author does not use Antigravity in the fork; the PR was generated by
unified_agent before the ToS was known.)

### Approach A1: The direction-of-call unblock — the strongest element of the pitch
The banned pattern is a third-party **client** consuming Antigravity's credentials
and quota. unified_agent is an MCP **server** that the Antigravity client calls
*out* to. Antigravity runs as itself, authenticates as itself, spends its own
quota, and gains tools. MCP is Antigravity's own documented extension mechanism
(`~/.gemini/config/mcp_config.json`). Three months of continuous use, no incident.

Consequence for T3 Code: **Theo cannot ship Antigravity as a provider, and does
not have to.** If a user runs Antigravity normally against a unified_agent hub,
that work lands in the backend's task queue, memory, and audit ledger — and a
control surface can display it without ever touching Antigravity OAuth. T3 Code
gets Antigravity visibility through the open door precisely because it never
opens the closed one.

Caveat to state plainly rather than paper over: the ToS language is broad, and
three months without a ban is evidence, not proof of Google's position. The
direction-of-call argument is strong and must be *made explicitly*. Theo makes his
own call; hand him the argument, not a reassurance.

### Approach A2: Pitch the pairing to Theo — CHOSEN
T3 Code is the client, unified_agent is the backend, and both rest on the same
premise about developer preference. Lead with the verified orchestration result
(33 PRs, 5 repos, 5 days, no CI, agent-authored, all green) rather than a feature
list, and ask one question about whether the backend belongs under T3 Code.
- **Effort:** S (human ~1 day / CC ~2 hrs, mostly packaging the demo). **Risk:** Low.
- **Reuses:** everything already built; nothing new to write.
- **Pro:** uses the warm channel with the right artifact; the pairing argument is
  structural rather than a favour being asked.
- **Con:** it is a conversation, not a shipped thing — outcome depends on one
  person's interest.

### Approach B: Governance layer as an installable T3 Code extension
Make `uaControlCenter.ts` configurable rather than hardcoded to one Tailscale
address; package approval gate + per-agent identity + audit so any T3 Code user
can point at their own hub. Reuses `approvals.py`, per-agent tokens, audit rows,
existing gate call sites.
- **Effort:** M (human ~2 weeks / CC ~2 days). **Risk:** Med.
- **Status:** immediate follow-on to A, not discarded.

### Approach C: Hosted governance backend with per-user keys
Per-user key acceptance, multi-device over Tailscale, audit rollup; T3 Code users
register against a backend. The Q6 thesis fully realized and the only option with
a revenue mechanism.
- **Effort:** L (human ~2–3 months). **Risk:** High — credentials, uptime, and
  liability for other people's fleets at n=1.
- **Status:** deferred until B produces external users.

### Approach D: Keep it private — rejected
Rejected because it would be the third withdrawal in three weeks and forecloses a
channel the author already has code inside of.

## Recommended Approach

**Customer discovery first. Open-core second. Build third.**

The substrate is done and verified. What is missing is one named person who states
the requirement with budget attached, and no amount of building produces that. The
author is uniquely positioned to get it at zero build cost, because the
conversations are already scheduled.

Sequence:
1. **Five discovery conversations** inside the existing pipeline, asking one
   non-leading question about what risk needs to see before approving agent work.
   Cost: zero engineering. Output: a named champion, a named blocker, and the
   requirement in the buyer's own words — or the discovery that the pattern is
   softer than it sounds, which is equally valuable.
2. **Theo, in parallel** — different buyer, different motion, no dependency. The
   pairing message stands (client/backend, the direction-of-call unblock, one
   question). Developer-side adoption is the free tier of the open-core shape.
3. **Then build the paid layer**, aimed at whatever the five conversations
   actually said, rather than at what the codebase already does.

Approaches A (Antigravity provider) and A2 (pairing pitch) are not discarded — A2
becomes step 2. What changed is that neither is the *company*. The company is the
attribution and evidence layer, and it needs a named buyer before it needs code.
