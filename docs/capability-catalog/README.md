# Unified-Agent capability catalog and ledger

Canonical, evidence-backed inventory of Unified-Agent capabilities. Useful to
The operator today (one source to answer "what exists, what state is it in, who uses
it") and safe to become the source for later customer-facing discoverability.

## Files

| Path | Role |
|---|---|
| `catalog.json` | **Authoritative structured catalog.** Edit this file only. |
| `catalog.schema.json` | JSON Schema documenting the item contract (documentation + external tooling). CI enforcement lives in the validator. |
| `catalog.md` | Rendered human view, generated by the validator (`--render`). Never hand-edit. |
| `../../scripts/validate_capability_catalog.py` | Deterministic, dependency-free validator + renderer. Source of truth for CI. |
| `../../tests/test_capability_catalog.py` | pytest wrapper exercising the validator and the acceptance criteria. |

## How to read an item

Every catalog item carries:

- `family` — one of the ten required capability families (see `families`).
- `customer_purpose` — operator/customer-relevant one-to-two sentences.
- `origin` — the task, PR, ADR, decision, or current source seam it came from.
- `implementation_state` — one of: `shipped-and-used`, `shipped-but-unconsumed`,
  `partially-wired`, `dormant/uncertain`, `superseded`, `speculative`, `blocked`.
  Code presence alone is never `shipped-and-used`.
- `consumer` — the named human/agent/SDK workflow that actually reaches it, or the
  literal `no verified consumer`. A historical emulation is never promoted to
  `shipped-and-used` without a current source path, callable entry point, real
  consumer, and current evidence.
- `entry_point` — the exact MCP tool, CLI command, route, library, or event hook.
- `connection_state` — one of `live`, `degraded`, `error`, `unknown`, `dormant`,
  `misconfigured`, `blocked`, `not-applicable`. **Never inferred from code or
  configuration alone** — it reflects the live evidence actually obtained.
- `evidence` — at least one row; each row is one of `code`, `test`, `ci`,
  `deployed`, `live` with a ref and, for live rows, an ISO date.
- `boundaries` — security, identity, approval, privacy, release, and
  tenant/workspace boundary facts.
- `incomplete` — required whenever the item is not `shipped-and-used`: owner,
  smallest next action, and an explicit non-action when resurrection is not
  justified.
- `wedge` — `evidence-wedge` (governance/evidence/control wedge) or
  `expansion-slice`.

## Verification layer (UA #1067)

The consumer surface (`GET /api/capability-catalog` and the Web Capabilities pane)
derives a canonical verification classification from the recorded fields and dated
live evidence. A `connected-and-live` classification is only ever derived when the
catalog itself records a dated `live` evidence row — never from config or tests
alone. Absent consumer or evidence is listed explicitly; every gap resolves to an
existing task ref, queue_coverage link, or named next action. Recommendations are
review-only suggestions; nothing auto-dispatches, auto-approves, or mutates tasks.

## Update procedure (for a future agent)

1. Read the enterprise spec `#1061`, the parent follow-up `#1064`, and the four
   2026-09-17 evidence captures (tasks `#1057`–`#1060`), plus current
   `README.md`, `docs/architecture.md`, `docs/security.md`, and the live queue.
2. Recheck `origin/main` against the recorded `freshness.source_baseline_sha` and
   update `freshness` (new `as_of`, baselines, live-check time).
3. Run the live read-only probes available to you; set each item's
   `connection_state` from that evidence — never from code/config alone.
4. Edit `catalog.json` only. Do not hand-edit `catalog.md`.
5. Run `python scripts/validate_capability_catalog.py --render` from the repo
   root; it must exit 0 and will rewrite `catalog.md`.
6. Update this page's summary numbers if totals changed.
7. Review `queue_coverage` before adding an item so no duplicate work is filed.
8. Run the focused test + lint gates that CI runs for this artifact.

## Browser boundary

Browser is a separate project. Unified-Agent has a narrow receiver wrapper
(`tools/projection.py` `browser_derive_task_reference`) and a manifest-only,
default-off connector entry. The wrapper revalidates a `focus_anchor`, checks
that its target task exists and is non-terminal, and derives a
`task_reference`; it does not persist the record. The connector appears in the
package projection and reports DORMANT without an active Horizon 2
registration. It rejects Horizon 2 registration and authorization, and doctor
stays DORMANT even if a stale active row exists. No authenticated Browser
client is verified to invoke it, and the tool remains limited to the steward
and chief-of-staff profiles. Nothing here implies a customer capability or a
live connection; the Browser SDK lane `#1045`–`#1055` owns that project's
roadmap.
